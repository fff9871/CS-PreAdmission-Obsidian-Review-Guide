# 程序查询与中断驱动I-O（★★★）

#computer-organization #io-system #interrupt

## Overview Table

| 方式 | CPU 如何等待 | 数据传送主体 | 优点 | 代价 |
|---|---|---|---|---|
| 程序查询 | 反复读取设备状态 | CPU | 简单、可预测 | 忙等浪费 CPU |
| 中断驱动 | CPU 做其他工作，设备就绪后中断 | CPU 执行服务程序搬运 | 提高 CPU 利用率 | 每次中断有保存/恢复开销 |

## 程序查询

    CPU读状态 ─未就绪→ 再读状态 ─...─→ 就绪 → 读/写数据

适合极简单、等待很短或启动早期尚未建立中断系统的场景。

## 中断驱动

    CPU启动设备 → 继续执行其他程序
                       ↓ 设备完成
                   中断请求
                       ↓
          保存断点/状态 → ISR处理数据 → 恢复执行

中断让设备主动通知 CPU，但数据量很大时逐字/逐事件中断仍可能造成高开销。

> [!warning]
> 中断驱动并不意味着 CPU 完全不参与数据传送；传统中断 I/O 中 CPU 仍执行中断服务程序读写接口寄存器。大量块数据更适合 DMA。

## Exam/Test Patterns

| 场景 | 回答 |
|---|---|
| CPU 持续读状态位 | 程序查询/轮询 |
| 设备完成后通知 CPU | 中断驱动 |
| 高频大块数据 | 中断次数过多，考虑 DMA |
