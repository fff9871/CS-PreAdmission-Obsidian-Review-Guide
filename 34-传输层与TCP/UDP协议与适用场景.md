# UDP协议与适用场景（★★★）

#computer-networks #transport-layer #udp

## Overview Table

| 特性 | UDP |
|---|---|
| 连接 | 无连接，无握手 |
| 数据模型 | 面向报文，保留应用报文边界 |
| 可靠性 | 尽最大努力，不保证到达、顺序和去重 |
| 首部 | 源端口、目的端口、长度、校验和，共 8 B |
| 控制机制 | 无内建重传、流量控制和拥塞控制 |
| 通信方式 | 支持单播、广播和组播 |

## 为什么选择 UDP

- 建立时延低、状态少、首部开销小。
- 应用可自行定义重传、顺序、前向纠错或过期丢弃策略。
- 适合实时音视频、DNS 等更关注及时性或请求很短的场景。

## 与 TCP 的工程取舍

| 需求 | 更常见选择 |
|---|---|
| 文件、网页正文、事务数据完整性 | TCP 或基于可靠传输的协议 |
| 实时语音、游戏状态、组播 | UDP 或基于 UDP 的定制协议 |
| 同时需要低时延与可靠性 | 可考虑 QUIC 等在 UDP 上实现可靠与拥塞控制的协议 |

> [!warning]
> UDP 本身不保证可靠并不等于“使用 UDP 的应用一定不可靠”。应用层可以增加确认和重传；反过来，UDP 也不意味着可以无视拥塞，互联网应用仍应实施拥塞控制。

## Exam/Test Patterns

| 关键词 | 回答 |
|---|---|
| 语音/视频为何常用 UDP | 低时延、允许少量丢失、过期数据重传价值低 |
| DNS 为何常用 UDP | 请求响应短、避免握手；大响应或特定操作也可使用 TCP |
| UDP 丢包 | 应用按需求重传、纠错或容忍，而非协议自动恢复 |
